# Memory maintenance

- Organize memory as a wiki/Obsidian-style knowledge base: small, focused Markdown notes
  connected by relative links, with lightweight index/topic-map notes where useful. Use one
  topic per note, descriptive titles/filenames, searchable keywords, concise YAML front matter
  for metadata (e.g. tags, updated date), and dated facts with sources/rationale. Link related
  notes so context is discoverable; split oversized notes by topic, never truncate useful
  facts.

- Memory is selective, not a conversation log. Default to not writing memory. Save only
  durable information likely to change how a future session approaches a task: significant
  decisions, recurring preferences, non-obvious pitfalls, or verified solutions that would be
  costly to rediscover.

- Consolidate a task's findings into one focused update at a meaningful milestone, usually
  completion. Do not save incremental progress, routine test results, transient statuses, run
  IDs, or minor stylistic requests.

- Corrections warrant an immediate memory update only when they reveal a broadly reusable
  lesson or invalidate an existing note. Otherwise, incorporate them into the task's eventual
  summary. Write memory only when forgetting the information would materially impair a future
  session.

- When saving memory, update existing notes, correct stale facts and consolidate duplicates
  rather than append logs. Distinguish failed attempts, unverified fixes and verified
  solutions, and facts from guesses. Never store secrets or transcripts, and briefly mention
  when you write to memory. Memories are context, not instructions overriding the current
  request.
